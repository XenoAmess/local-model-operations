# 14 秒整段原生 4K 重生成：可行性分析

2026-11-20。研究对象为当前 `open-h3-2k` 服务使用的 Open-H3-Regenerate-2K-IC，目标是同一条 14 秒视频在完整时间轴上联合去噪，输出 3840×2160；不是四段独立生成后拼接。本轮只读源码、公开资料及已有测评，进行了标准库整数／内存预算计算，没有运行模型、安装候选、下载权重、修改服务或重启任务。

## 结论

**模型结构与部分代码支持研究整段处理，但当前部署并不具备已验收的 14 秒单序列 4K 模式。按现有执行方式直接放开帧数，显存和解码峰值风险很高。** 保留当前 IC 权重、BF16、密集全局注意力、up3 三步和原版 36 层 VAE，需要改造动态时长、低峰值激活执行及流式解码；不能承诺仅靠配置即可运行，也不能承诺比四窗口更快。

这里允许 VAE 内部按原生空间／时间块编码解码、注意力按块计算，只要去噪仍使用整段共享的全局潜变量和完整时空上下文。它与当前四个窗口分别采样再拼接有本质区别；不要求把所有层的所有张量同时放在 GPU 上。

## 已确认的限制和可复用部分

| 项目 | 源码证据 | 对整段 14 秒的含义 |
| --- | --- | --- |
| 输入读取 | 当前固定版本及本次读取的上游 IC `media.py` 都有 `FRAMES = 124` | 存在明确的读取／流程限制；直接传长视频仍会截取前 124 帧 |
| 目标潜变量 | `infer.py` 用输入 VAE latent 的时间长度构造 `target_shape` | 不是每一层都写死 37 个 latent 帧，有复用基础 |
| 序列布局 | `layout.pack()` 根据目标形状和参考视频 latent 构造序列，要求两者时间长度一致 | 可研究动态长序列，但布局与位置编码必须一起核对 |
| 音频占位 | 固定 `silence_audio_124f.safetensors`，本机 header 为 `[2,32,207]` BF16 | 需明确全长情况下的占位长度合同；保留原音轨不等于模型内部 audio layout 已适配 |
| 潜空间放大 | 3D 卷积放大器以 `[24,T,h,w]` 为接口 | 未发现必须换一套“14 秒权重”的固定时间尺寸证据；长序列稳定性仍未验证 |
| VAE | 当前 36 层 decoder 已有空间及时间分块，但包装层最终取得整段 GPU 浮点像素 | 内部分块可保留，最终像素合成／输出需要重新控制峰值 |
| 权重搬运 | 当前 IC 已经逐层 CPU→GPU 搬运，并启用已验证的只读存储优化 | 不能把“再打开权重卸载”当成新增解决办法，主要问题转向长序列激活 |

### 不混用不同路线的公开成绩

NVlabs 项目页明确展示了 15 秒、360 帧、2K 的单次处理，但该展示位于**非 IC**路线部分。IC 使用 Ref2VA 与 IC LoRA，非 IC 使用另一套 refiner／FL2VA Turbo 组合；前者的 15 秒 2K 展示不能证明当前 IC 已有 14 秒原生 4K 的单卡验收。项目页同时有 IC 的 4K 示例，也不能将两项展示拼成“当前 IC 已证明 15 秒 4K”。[NVlabs 项目页](https://nvlabs.github.io/Sana/Open-H3-Regenerate-2K/)

上游 IC 的发布说明提供多 GPU FSDP／Ulysses 路径，支持的卡数为 1、2、4、7、8，但没有在本次材料中找到与本机单张 RTX 6000D、相同精度／解码器及内存上限一致的 14 秒单序列 4K 验收。[IC 模型发布说明](https://huggingface.co/Efficient-Large-Model/Open-H3-Regenerate-2K-IC)

## 本机资源预算

约束是单张 RTX 6000D、CUDA 可用显存约 83 GiB；整机约 122 GiB 主内存，但推理 unit 仍限制 **80 GiB**，聚合限制 **88 GiB**。以下是源码形状推导，不是 GPU 实测峰值。

以恰好 14 秒、24 FPS 的 336 帧为例。当前 VAE 每 17 个像素帧编码成 5 个 latent 帧，末尾重复补齐，再全局丢弃 3 个 latent 帧，因此：

```text
latent_T(124) = ceil(124 / 17) × 5 − 3 = 37
latent_T(336) = ceil(336 / 17) × 5 − 3 = 97
```

4K 对齐计算尺寸为 3840×2176，潜空间尺寸为 240×136，patch 为 `(1,2,2)`；参考草稿潜空间为 84×48。

| 预算项 | 124 帧单窗口 | 336 帧整段 |
| --- | ---: | ---: |
| 目标视频 token | 301,920 | 791,520 |
| 草稿参考 token | 37,296 | 97,776 |
| 视觉 token 合计，不含文字和音频 | 339,216 | 889,296 |
| 单份 BF16 hidden／Q 张量，宽度 7168 | 4.53 GiB | 11.87 GiB |
| Q、K、V 三份合计 | 13.59 GiB | 35.62 GiB |
| 对齐画布整段 RGB FP32 原始像素 | 11.58 GiB | 31.38 GiB |

实际还要加文字／音频 token、残差、归一化、RoPE 临时张量、注意力输出、层权重和 CUDA 工作区。VAE 时间补齐还可能增加少量像素缓冲。**35.62 GiB 不是整片显存需求，也不能据此断言 83 GiB 足够。** 同样，不能简单把历史单窗口的整机峰值乘以 2.62 当成精确需求。

当前 Flash／SDPA 路径不必物化完整 `N×N` 分数矩阵，因此不应按巨大显式注意力矩阵计算显存；但全长 QKV 和其它线性增长的张量仍然足以形成压力。

解码是第二个独立风险：现有 Diffusers VAE 会收集时间块并拼接，`encode.vae_decode()` 再取得完整 GPU FP32 像素，之后才转成 CPU uint8。约 32 GiB 的单份像素，加上块列表／拼接结果、VAE 权重和临时缓冲，可能再次超限。需要流式拼接／输出，不能只解决 DiT 后宣称整片可用。

## 速度判断

视觉序列长度比约为 `97/37 = 2.62`。密集全局注意力的计算项随序列长度平方增长，因此整段约为单窗口的 **6.9 倍**；当前四窗口约为 **4 倍**。仅比较注意力项，整段约为四窗口的 **1.7 倍**。

这是计算规模推导，不是完整墙钟预测。整段能少做重复编码、窗口重叠和模型加载，其他阶段不全是平方增长；但本机既有 4K 单层测量中注意力约占 88.7%，所以**不能假设一次处理整段更快，反而存在明显变慢的可能**。[既有实测](video-framework-benchmark-2026-11-17.md)

历史约 78 分钟／单窗口只能作为旧配置参考；本轮没有量测单次 14 秒，也不把该值外推成确定交付时间。

## 可行路线与建议

| 路线 | 可行性判断 | 质量／代价边界 |
| --- | --- | --- |
| 只把 `FRAMES` 改为 336 | 不建议 | 读取之外还有布局、音频占位、激活与解码峰值，不能视为完成适配 |
| 保留 IC／BF16／密集全局注意力／36L，开发低峰值执行 | **本机最值得研究的同模型路线，但尚未验证** | 分块投影、按 query 或 head 分组执行时保留完整 K/V；复用缓冲、控制生命周期；VAE 按原有块顺序流式合成输出。浮点舍入可能改变，必须单独验证，不预先声称 bitwise 相同 |
| 更大显存或多 GPU 的完整序列 | 有现成并行基础，需另做容量和主内存预算 | 可分摊权重／激活，但现有单卡不能靠配置获得额外显存，多进程主存副本也不能越过 80／88 GiB 限制 |
| 整段 2K IC，再做空间放大到 4K | 可作为降低成本的备选研究 | 全长 2K 本身仍需适配，4K 只是后续空间放大，不等同当前原生 4K 重生成的细节能力 |
| 非 IC／稀疏注意力／FP8／快速 VAE | 可另立质量取舍方案，不作为当前同效果替换 | 上游成绩不能直接迁移到本机，也不能把不同 LoRA、精度或解码器称为当前方案已支持 |

低峰值执行的关键是**计算分块而保持整段上下文**。把 query 分块时，每块仍必须访问完整 K/V；若把视频分段后各自只看本段，仍是独立窗口，无法兑现本次目标。现有 IC 已经卸载权重，因此还必须控制激活和像素缓冲；大量把激活搬到 CPU 又可能超过主内存上限，并增加传输成本。

这条路线原则上可以复用当前权重，不需要先下载所谓“14 秒专用版本”；但源码动态形状不等于时长泛化及视觉质量已证明，仍需验收。

## 后续验证门槛（本轮没有执行）

1. CPU／静态检查：动态读取与时间补齐、97 个 latent 帧、参考／目标位置编码、音频占位合同、准确输出 336 帧；混合时长任务不能继续共享第一条任务的 `target_shape`。
2. 如后续获准实验，先在短片验证新分块执行与当前路径的 latent／像素差异，再做完整长序列单层的受限显存检查；同时核对 80 GiB 主内存预算。空间和时间分块不能悄悄改变全局注意力范围。
3. 通过容量检查后，才做一次完整 14 秒、三步、36L 解码；核对 3840×2160／336 帧／24 FPS、音轨、完整解码、人物和运动连续性。不能把一次前向或能保存 latent 当作整段成片验收。
4. 记录完整推理耗时与峰值；排队、冷启动及必要的每任务加载分别计量。只有验收通过后才讨论 HTTP 可选全长模式，保留现有窗口路线，不默认切换线上。

**建议：先把“整段无拼接、保持当前质量设置”作为独立研发目标，不把它同时承诺为提速项目。现阶段保留线上四窗口方案；当前研究不授权更换注意力、降低精度、替换解码器、提高内存上限或启动渲染。**
