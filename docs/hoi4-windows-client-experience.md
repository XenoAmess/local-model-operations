## 可复用的诊断次序

1. 先检查失败入口的实际字节和格式。该次 `bin/opencode.exe` 只有479字节，是提示postinstall未运行的shell文本，没有MZ/PE头；不能仅因扩展名或包管理器安装成功就认定可执行程序存在。
2. 核对包管理器实际构建许可和已解析原生依赖。该次全局许可明确为 `allowBuilds: { opencode-ai: false }`，而同版本原生程序已安装。许可、依赖版本和入口状态共同解释故障，不从症状直接猜测架构不支持。
3. 修复前验证实际硬件与候选程序。该次用Windows系统函数确认AVX2，并先运行已安装同版本x64原生程序的版本命令；随后用临时硬链接和原子替换恢复入口。此做法描述历史处置，不是跨版本默认安装脚本。
4. 限定权限变更。该次只允许 `opencode-ai` 的构建脚本，没有全局开放所有包、修改用户认证资料或改写厂商脚本。
5. 读回真实CLI结果。源程序、恢复后的入口与PATH中的CMD入口均返回 `1.19.4`、退出0；help有实际内容。该版本help写到stderr，因此同时核stdout、stderr与退出码。
