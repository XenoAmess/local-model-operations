# 保持现有 H3 模型的工程优化参考

2026-11-21。用户询问纯工程提速方式。本轮只读现有实现、已完成计时及官方资料，没有启动新 GPU 测试、安装依赖、修改线上配置或中断后续任务。保持完整 IC、BF16、原采样器／步数、完整时间轴和原版 36L FP32 解码器。

## 先确定能够省掉的时间

S48 实际 worker 总计 29,247.78 秒，其中采样 27,987.1 秒（95.69%），原版 VAE 解码及无损输出 989.7 秒（3.38%），其它加载、封装等合计约 270.98 秒（0.93%）。[实际验收与短测](h3-full-sequence-validation-and-dense-benchmark-2026-11-21.md)

即使假设解码完全免费，也只节省约 16.5 分钟；解码快一倍约省 8.25 分钟。这里的 95.69% 是**采样**占比，里面还有 FFN、LoRA、投影和搬运，不能冒充已实测的注意力占比。把代表性注意力调用按查询总量及 150 层次外推，注意力约占总时长 92%，但这只是定位方向的估算，仍需要真实层的算子分析。

## 优先级与适用边界

| 方向 | 可实施的工程工作 | 对本机的判断 |
| --- | --- | --- |
| 1. 真实层性能分析 | 用 Nsight Systems 看 CPU／拷贝／计算时间线，用 Nsight Compute 看 Tensor Core、显存吞吐、寄存器和 warp 停顿 | 最值得先做；分析本身不提速，目的是确定哪种内核改造有收益，不能把 GPU 利用率 100% 当成达到峰值 |
| 2. 密集注意力底层调优 | SM120 的矩阵 tile、warp 分工、流水级数、布局、共享内存和 softmax 调度；比较不同的新密集实现 | 最接近占大头的计算，但收益未知、研发成本高，保持同一公式也不保证浮点逐位相同 |
| 3. 保留 36L 的解码／编码流水线 | 原像素直接送给最终编码器，解码与 CPU 编码重叠，减少中间视频的重复编解码和落盘 | 当前确有 FFV1 中间文件再转 H.264 的路径，属于具体可优化点；不换解码器、不减少帧，收益受上述时间占比限制 |
| 4. 有边界的权重预取 | 在已有单向 H2D 搬运之上，用小型 pinned staging buffers、独立 stream 提前传下一层 | 可以争取保持同样运算；需要正确同步和额外缓冲。不是固定整模型内存，不新增激活卸载，继续遵守 80／88 GiB 上限 |
| 5. 静态缓冲与 CUDA Graphs | 固定大小缓冲复用，录制现有计算内核序列，减少 CPU 发射、分配与同步开销 | 适合多小算子的 CPU 空洞；当前单次长注意力约 3.1 秒，调用墙钟与 CUDA event 只差几十微秒，不能期待图捕获把该调用变快数倍 |
| 6. 阶段复用和缓存 | 在现有模型分组队列基础上，进一步批量编码／去噪／解码，复用相同素材的编码结果 | 对批量吞吐和重复输入有用；减少每请求阶段加载，不用首次启动时间冒充量产收益。对这条八小时任务的绝对收益较小 |

Nsight 的吞吐和 Roofline 指标可以区分 GPU 是否受计算、访存或其它资源限制。性能计数器采集可能重放内核并扰动时间，正式收益仍需用不挂 profiler 的预热后计时确认。[NVIDIA Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)

### 密集内核还有哪些未覆盖的候选？

本次只实测了已安装的 PyTorch FlashAttention、cuDNN 9.20 路径和 FlashInfer 0.7.2 FA2，不能推成“所有密集内核都没有空间”。最新 SM120 FROST／CuTe 实现和 FA4 的适配／调参可以作为候选，但尚未在本机的百万 token 形状下验证。

NVIDIA 提供实验性的 SM120 FROST attention AOT 接口，有 BF16 非因果 D128 路径及 tile／split 选项。**AOT 提前编译本身主要改变启动和构建成本，不能算预热后的计算提速**；真正要比较的是所选内核的执行时间。它对完整长度、MHA 布局、工作区、驱动及工具链的适配仍要检查，不能只看 SM120 字样就宣布可用。还必须重做末尾 K/V 与大偏移测试，避免重复本次 FlashInfer 超长 HND 的静默错误。[NVIDIA SM120 AOT／FROST 说明](https://docs.nvidia.com/cudnn/operations/Attention/aot_sm120_attention)

调整块大小不等于改变注意力范围：每个查询仍须看到全部 K/V。但当前 Q 已按 16,384 分批，单纯把 Python 循环次数从约 58 次减少，不能消除注意力的平方级配对计算。是否值得改块大小取决于底层吞吐和显存，不保证更快，也不能跳过数值比较。

### 解码／输出流水线的具体位置

[当前流式输出](../deployments/video-generation/tools/h3_full_sequence.py) 将原版 VAE 的 RGB uint8 帧送给 FFmpeg，生成 FFV1 MKV；[完整序列 worker](../deployments/video-generation/tools/h3_2k_worker.py) 再读该文件，以 libx264 medium／CRF16 编成最终 MP4。这保留了无损中间结果，但多一次中间编解码和 I/O。

候选做法是保持原 VAE 帧及裁剪顺序，将相同像素流送入参数相同的最终编码器，音轨另行保留／封装。保留 latent 检查点以支持失败后重解码。必须核对完整帧数、时间戳、音轨与解码后的像素；不能把改用 NVENC 或换 24L decoder 默认当成输出完全一致。这个方向可以省去部分后处理时间，无法省掉七个多小时的采样。

### 异步预取与图捕获的代价

异步传输与计算重叠需要 pinned 内存和合适的独立 stream，同步和源缓冲生命周期必须正确；固定内存不应过量使用。[CUDA Best Practices](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html)

CUDA Graphs 主要减少 CPU 设置／发射开销，要求稳定的形状、地址和控制流。当前逐层权重卸载会改变张量地址，不能直接全模型捕获；应先做固定 GPU staging 或局部图，再检查同一内核序列的结果。[PyTorch 2.12 CUDA Graphs](https://docs.pytorch.org/docs/2.12/notes/cuda.html#cuda-graphs)

`torch.compile`、算子融合、改变 GEMM 形状同样属于工程实现，但可能改变舍入。FastVideo 官方 H3 的一次 regional compile 实验虽更快，与 eager 对照 SSIM 只有 0.7108；这不是审美排名，却足以说明“只改代码”不自动等于原输出一致。融合若要保持位级一致，需要保留原先各步的精度转换、舍入边界和运算顺序。[FastVideo 编译准确性说明](https://haoailab.com/FastVideo/inference/optimizations/)

## 已做的、不可误包装为无损的

- BF16 LoRA 转换缓存、只读 CPU 权重存储、单向传输、FFN 输出预分配已经部署，且有真实层位级对照；这不是新的待实现方案。[已采用优化](../deployments/video-generation/docs/open-h3-exact-performance.md)
- 全片 encoded／采样步／latent 检查点和原版 36L 流式解码已经接入，主要提供复用和失败恢复。缓存必须绑定素材、模型、尺寸、caption、seed 与相关编码配置，不能换种子后偷偷复用随机采样结果。
- 跨去噪步缓存 DiT 的 K/V、TeaCache 类近似复用、稀疏注意力、量化、减少步数／帧数、换快速 VAE，都不属于本报告承诺的同结果优化。
- 更多 GPU 上的上下文并行是另一条工程路线，但需要额外硬件和数值验收；当前单卡的多 stream 或多服务并发不会自动增加计算资源。此前 4K 代表注意力并发测试没有吞吐收益，不重复当作新方案。

建议先分析一层真实长序列，再决定是否投入密集内核调优；同时可把解码到最终 MP4 的流水线作为独立、小范围的优化。新方案须先核对算子和实际层，再验证完整视频，不能将局部提速直接当成整片收益。当前没有新的已验证加速幅度，也没有自动改动正式服务。
