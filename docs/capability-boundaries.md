# 能力证据与采用分级

本页用于决定下一项真实任务如何分工。结论绑定模型标识、日期、实际输入、输出范围、owner 修正和验证环境；一次成功或失败都不构成永久能力上限。下列历史模型标识为 `qwen38-coder`，记录没有固定权重、量化或服务构建版本，不能将这个别名当作可复现的权重版本。

## 将不同证据分开

| 层次 | 可以记录的事实 | 仍需独立证明 |
| --- | --- | --- |
| 传输 | 实际请求、完整 SSE、stop / length、usage | 候选正确、源码采用 |
| 源审 | 类型、调用合同、数据流、输出范围逐项核对 | 编译及行为 |
| 编译 | 指定源码、依赖、参数和编译器实际通过 | 分支、负例、资源及并发行为 |
| 有限验证 | 指定输入、oracle、环境和断言通过 | 未覆盖分支、其它机器或完整系统 |
| 正式采用 | 精确文件和 commit 已发布或装载 | 实际线上结果与性能收益 |
| 业务执行 | 真实动作、后态和持久结果 | 不能由前面任何一项代填 |

这些是独立记录维度。未编译的源审拒绝不能记成 javac 失败；HTTP stop 也不能记成已采用。源码候选调用器不提供自动工具执行闭环，provider 的普通文本接口成功不证明 tool parser、自动测试或业务控制能力。

## 按实际采用单位署名

| 等级 | 应写清的范围 |
| --- | --- |
| 整份原样采用 | 一次完整回答中的目标源逐字采用；格式或注释若改动也单列 |
| 完整方法原样采用 | 只授该方法；机械框架、装配和其它方法分别署名 |
| 有限 hunk 采用 | 每个独立完整纠正块的原件、唯一匹配位置和最终差异 |
| 部分采用，加 owner 修正 | 模型保留部分；owner 的类型、机械、语义、oracle 或装配成本分别列出 |
| owner 完整接管 | 模型源码采用0；保留失败回答、诊断与原件，不因最终验证通过追认模型实现 |
| 分析参考 / 未选用 / 拒绝 | 分开记录；可读分析不是生产代码采用 |
| 未审 / 尚未验证 | 保留未知，不用默认字段或后到结果改写旧截止点 |

“owner 算法改动0”只描述算法差异，可能仍有 imports、命名空间、框架或 fixture 成本；它不等于整类逐字采用。多个方法、分析输出、测试和生产文件的分母不同，不拼成一个采用率。部分流或 length 候选整次丢弃，不能从中剪正确片段获得采用信用。

后到编译、验证和发布另附带时刻的记录，引用原始 source SHA。冻结的 SOURCE_READY 仍保留当时“未编测”的事实。[历史后到回执例](https://github.com/XenoAmess/ck3_eternal_recurrence/blob/0958f36720a2cf75d1e3ede84ff3ae7fa730d91d/docs/local-model-capability-boundary-2026-10-28.md#L132-L140)

## 输入缺失与输出错误分别归因

先审实际 REQUEST 的三个消息，再审候选。manifest 中有文件、另一角色读过文件、任务写了一个全限定名，都不能证明本角色已收到所需声明。沿继承关系找到成员和常量的直接声明者，包含实际 overload、record accessor、名义返回类型、调用点与下游约束。

| 观察 | 归类与下一步 |
| --- | --- |
| reset、无完整终态、provider 不支持 tool parser | 传输或服务接口问题；按 [重试规则](concurrency-and-retries.md) 处理 |
| length、重复正文、占位值回显 | 保留输出失败；核预算、活动输出合同和提示示例，不拼半流 |
| 缺祖接口、漏 callee、旧签名、实际参数未转发 | owner 输入或工具闭包成本；补实际声明，保原错误请求 |
| owner oracle 的字节宽度、地址、符号或分支错误 | fixture / 反馈成本；单独勘误，不能算完整正确提示下的模型失败 |
| 完整正确声明已给，仍造 API、错类型、丢返回状态或错分支 | 具体模型候选错误；有限纠正或 owner 接管 |
| 结论尚无证据 | 写未知；不从模型叙述、缺日志或相邻任务补事实 |

同一回答可同时有输入缺口与其它独立语义错误，应逐项保留，不能互相抵销。实际请求确已装入纠正任务而回答仍重复，也只记录可见事实，不推断服务缓存原因。

2026-11-01 新增预算教训：caller 传64MiB，而 callee 仅允许最大8MiB；callee 先验预算参数，连小包也会拒绝。分别验证 **预算参数属于 callee 的允许范围** 与 **实际包体字节不超过获准预算**，提供 caller、callee 及 MAX 常量的真实声明。多个 owner 静态审阅和 strict / DTO 通过，仍不足以证明公开捕获链可用；补一条通过真实公开入口的窄回归。原模型输入漏了 callee，此成本不能改成“完整输入下的模型失败”，也不据此全局放大限制。来源为执行者保管的独立 `PORTABLE-BUDGET-RULE220` 摘要，见 [来源说明](source-origins.md)。

## Oracle、状态与验证范围

独立 oracle 应先按原始合同冻结，再读新候选或实际输出。记录作者是否见过成熟参考、其它方法、生产实现或结果，以及首次暴露时刻。若先把 owner 的 literal oracle 放进请求，模型完成的是编码与装配，不能授独立推导 oracle 的能力；复用成熟框架也只授真实新增部分。

验证必须比较实际执行结果与独立预期，不能比较两个预制数组、自我比较、把未实现端口填0，或吞异常后仍报成功。确认 fixture 能走到所称分支，校验真实调用次数和完整副作用；checks、事件、case、业务语义断言分别计数。仅验证数据形状或能编译，不证明动态调用合同闭合。

跨 opaque 回调后用实际返回的当前状态继续，不反复借入口快照。未知字段保持未知或显式拒绝；有限寄存器投影不能冒充完整硬件。返回值无人使用也不表示无副作用；原始 read-modify-write 的读取、宽度和顺序不能任意抹去。[继承闭包与当前状态原规则](https://github.com/XenoAmess/ck3_eternal_recurrence/blob/0958f36720a2cf75d1e3ede84ff3ae7fa730d91d/docs/local-model-worker-guide.md#L262-L272)

| 任务与实际输入 | 模型及 owner 成本 | 已有验证 / 分工判断 |

### 2026-11-01：完整输入下的复杂状态桥接

一次真实任务要求围绕既有算法建立正常返回帧桥，算法仅执行一次，并保留所表示的寄存器、物理栈副作用和回调后的当前状态。当前 API 与既有算法的物理前缀为53,943字节，两次实际请求的第二消息均为其 LF 投影52,886字节；三消息完整保留源码内容。两次语义生成各限9,000输出 tokens，实际3次 POST 得到2份完整 stop 和1次连接 reset。reset 半流未读取或拼接；两份解码后的 Java 分别19,647和17,373字节，均不是 length 截断。

两稿在编译前源审中均被拒绝，模型 Java 采用0。首稿错用实际成员和帧布局，纠正稿仍缺寄存器参数、混淆读事件与回调状态，部分状态更新仅留占位注释。回答的修正说明不能替代实际赋值和分支核对。此例输入声明已提供，应与缺 API 的失败分开；审阅应核实际读事件的来源、回调携带的当前值及返回槽归属，有限纠正后如实记录 owner 接管。

后来的 owner 整体实现分别在两个 JVM 中通过3个直接见证方法（6个正常输入）及1个组合方法（1个正常输入）；没有把它们重跑或改写成同次4方法通过，也不追授模型源码成功。这是有限 Java 软件验证，不证明 Native、完整硬件状态、线上或性能结果，更不构成模型的永久能力上限。[脱敏案例摘要](evidence/2026-11-01-stateful-frame-bridge.json)与[来源限制](source-origins.md)保留这些口径。

### 2026-11-01：跨对象作用域审阅

两项具名源码覆盖任务分别提供21文件（20 Java及1版本说明）与24 Java，物理文件合计1,231,473 / 1,334,137字节，实际源码消息UTF-8为1,222,924 / 1,325,283字节；物理字节、消息字节和reported tokens分开。各一次POST完整stop，先后执行没有HTTP交叠。两份回答仅部分分析可用，模型源码采用0、无编测；大输入被接收不证明整图审阅完成。

实际错误包括把缓存hit说成重新完整读payload、给出错误源码行号、从局部链推全项目覆盖；旧“待采用”标签则有owner输入来源，不能全算模型自发错误。owner按同一实际Store、ThreadLocal与动态调用链确认原入口覆盖，另独立找到新增入口缺少范围包装，仅提出未采用、未测试文本候选。该有限源审不证明缓存物理安全或速度，详见[经验步骤](experience-log.md)和[脱敏摘要](evidence/2026-11-01-scope-callchain-audit.json)。

选择下一任务时逐步扩大真实改动、依赖传播或诊断范围，每一步保留必要负例；输出预算应允许一个完整方法或组件，过大范围则按真实职责拆分。不能让已完成任务再次出题来增加请求数，也不能把模型永久限定为机械替换。

### 2026-11-01：限定只读原生工具循环

用户修复服务并明确要求工具重测后，指定端点对7次真实POST均返回HTTP200；OpenCode1.18.31实际完成两文件read调用、两个tool结果回传和stop，CLI退出0。这支持限定只读原生工具循环，不授代码编辑、命令、业务动作或恢复策略。初轮JSON模式没有产生工具调用且文件哈希错误；直接auto路径三轮内出现一次重复读取，随后独立有界收尾分支正确消费工具结果中的四项标量，但分析文字仍有控制流和参数传递误判。字段核对、工具执行和整体审阅分别分级，代码采用0。[重测摘要](evidence/2026-11-01-native-tool-retest.json)与[更新预研](local-model-framework-research-2026-11-01.md#修复后的原生工具调用重测)保留实际参数、消息和边界。

接受过大输入只证明那次上下文被服务接收，不证明最大窗口或多文件自主实现。请求 `enable_thinking` 不证明内部模式启用，可见 reasoning 字段缺席也不证明无内部推理。不同输出预算、时间和并发下的两次耗时不能归因模式、缓存或加速；需要固定比较条件、实际 REQUEST 与可观测结果。[大输入及模式观察的原始限制](https://github.com/XenoAmess/ck3_eternal_recurrence/blob/0958f36720a2cf75d1e3ede84ff3ae7fa730d91d/docs/local-model-capability-boundary-2026-10-28.md#L37-L54)
